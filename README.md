# Mini NPU 시뮬레이터

3×3부터 25×25까지의 패턴이 십자가(Cross)인지 X인지, MAC 연산으로 판정하는 파이썬 콘솔 프로그램입니다.

## 1. 실행 방법

- 환경: Python 3.8 이상 (외부 라이브러리 없음, 표준 라이브러리 `json`, `time`만 사용)
- 파일 위치: `main.py`와 `data.json`을 **같은 폴더**에 둡니다.
- 실행: 터미널에서 `python main.py`
- 모드 선택: 실행 후 `1`(사용자 입력 3×3) 또는 `2`(data.json 분석)를 입력합니다.
- 모드 1 입력 방법: 필터 A 3줄 → 필터 B 3줄 → 패턴 3줄, 총 9줄을 입력합니다. 한 줄에 숫자 3개를 공백으로 구분하고, 줄마다 엔터를 누릅니다.
- 모드 1 예시 입력: 필터 A(십자가) `0 1 0 / 1 1 1 / 0 1 0`, 필터 B(X) `1 0 1 / 0 1 0 / 1 0 1`, 패턴(십자가) `0 1 0 / 1 1 1 / 0 1 0` (`/`는 줄바꿈 표시)
- 모드 1 예시 결과: 필터 A 점수 5.0, 필터 B 점수 1.0, 판정 A

## 2. 구현 요약

- **MAC 연산**: 이중 `for` 반복문으로 패턴과 필터의 같은 위치 값을 곱해 `total`에 누적합니다. NumPy 같은 라이브러리는 쓰지 않았습니다.
- **라벨 정규화**: `normalize_label` 함수가 `'+'`, `'cross'`는 `Cross`로, `'x'`는 `X`로 통일합니다. 앞뒤 공백과 대소문자 차이도 흡수합니다. 필터 키(`cross`, `x`)와 `expected` 값(`+`, `x`)에 같은 함수를 적용하고, 출력과 PASS/FAIL 비교는 모두 표준 라벨 기준으로 합니다.
- **동점 처리(epsilon)**: `EPSILON = 1e-9`로 두고, 두 점수의 차이 `abs(a - b)`가 이보다 작으면 동점으로 봅니다. 모드 1에서는 `판정 불가`, 모드 2에서는 `UNDECIDED`로 출력합니다.
- **예외 처리**: 키 형식 오류, 스키마 오류(`input`/`expected` 없음), 크기 불일치, 알 수 없는 라벨, 숫자가 아닌 값이 있으면 해당 케이스만 FAIL로 기록하고 사유를 남깁니다. 프로그램은 중단되지 않고 다음 케이스를 계속 처리합니다.
- **입력 검증(모드 1)**: 줄마다 숫자 개수가 3개가 아니거나 숫자로 바꿀 수 없으면 안내 문구를 출력하고 같은 줄을 다시 입력받습니다.
- **성능 측정**: `time.perf_counter()`로 MAC 연산 함수 호출 구간만 재고, 10회 반복한 평균을 ms로 출력합니다. 입력·출력·파일 읽기 시간은 제외했습니다.

## 3. 결과 리포트

### 3-1. 테스트 결과 요약 (data.json 분석)

전체 6개 케이스 중 **통과 3개, 실패 3개**입니다.

| 케이스 | Cross 점수 | X 점수 | 판정 | expected |
|---|---|---|---|---|
| size_5_1 | 0.9 | 0.9 | UNDECIDED | X |
| size_13_2 | 7.5 | 7.5 | UNDECIDED | Cross |
| size_25_1 | 4.9 | 4.9 | UNDECIDED | X |

### 3-2. 실패 원인 분석

1. 실패한 3개 케이스는 모두 Cross 점수와 X 점수가 **수학적으로 같은 동점**이라 판정이 `UNDECIDED`가 되었고, expected(Cross 또는 X)와 달라서 FAIL이 되었습니다.
2. 라벨/스키마 문제는 아니었습니다. `'+'`와 `'x'`는 정규화로 `Cross`와 `X`로 정상 변환되었고, 모든 패턴과 필터의 크기도 일치했습니다.
3. 로직 문제도 아니었습니다. 같은 코드가 나머지 3개 케이스(size_5_2, size_13_1, size_25_2)는 정확히 PASS로 판정했습니다.
4. 원인은 **데이터(필터 설계) 문제와 수치 비교 문제**의 조합입니다. 예를 들어 size_5_1의 X 패턴은 Cross 필터와 중심 한 칸(1.0 × 0.9)만 겹쳐 0.9점이 나오고, X 필터와는 값이 0.1인 9칸이 겹쳐 0.1 × 9 = 0.9점이 나옵니다. 그래서 두 필터의 점수가 같습니다.
5. 컴퓨터는 소수를 2진수로 저장하기 때문에 이 동점이 정확히 같은 값으로 계산되지 않습니다. size_5_1은 `0.9`와 `0.8999999999999999`, size_13_2는 `7.499999999999997`과 `7.5`, size_25_1은 `4.9`와 `4.899999999999999`로 계산되었습니다. 이것이 부동소수점 오차입니다.
6. 이 오차의 크기는 약 `1e-16`~`1e-15` 수준이고, epsilon(`1e-9`)보다 훨씬 작아서 동점으로 올바르게 처리되었습니다.
7. 만약 epsilon 없이 `>`로만 비교했다면 오차 때문에 아주 조금 큰 쪽이 승자로 뽑혔을 것입니다. 그 결과 size_5_1은 Cross, size_13_2는 X, size_25_1은 Cross로 판정되어, 오차에 따라 결과가 달라지는 불안정한 판정이 되었을 것입니다. (이 경우도 expected와 달라 FAIL입니다.)
8. 따라서 epsilon 정책은 "동점을 동점으로 인식"하게 해주는 장치이며, 이 3개의 FAIL은 프로그램 오류가 아니라 **점수만으로는 구분할 수 없는 데이터**라는 정확한 진단 결과입니다.
9. 개선 방법은 두 가지입니다. 필터 값을 조정해서 서로 다른 점수가 나오게 하거나(데이터 개선), 동점일 때 사용할 별도의 규칙(예: 추가 판정 기준)을 정의하는 것(정책 개선)입니다.
10. 이번 과제에서는 과제 명세대로 동점을 `UNDECIDED`로 처리하고 expected와 다르면 FAIL로 기록했습니다.

### 3-3. 성능 분석

MAC 연산을 크기별로 10회 반복한 평균 시간입니다. (3×3은 십자가 필터와 십자가 패턴 기준, 나머지는 data.json의 Cross 필터와 같은 크기의 패턴 기준)

| 크기(N×N) | 평균 시간(ms) | 연산 횟수(N²) |
|---|---|---|
| 3×3 | 0.004120 | 9 |
| 5×5 | 0.006030 | 25 |
| 13×13 | 0.016550 | 169 |
| 25×25 | 0.065330 | 625 |


### 3-4. 시간 복잡도 분석 (O(N²))

1. MAC 연산은 N×N 칸을 모두 한 번씩 방문하며 곱하고 더하므로, 곱셈 횟수는 항상 **N²번**입니다. 이것이 시간 복잡도 **O(N²)** 의 근거입니다.
2. 3×3에서 25×25로 커지면 연산 횟수가 9번에서 625번으로 약 **69.4배** 늘어납니다.
3. 측정 결과 평균 시간은 3×3이 0.004120 ms, 25×25가 0.065330 ms로 약 **15.86배** 늘었습니다. 크기가 커질수록 시간이 커지는 경향은 연산 횟수의 증가와 같은 방향입니다.
4. 측정 배율(15.86배)이 연산 횟수 배율(69.4배)보다 작은 이유는 함수 호출, 반복문 시작, 시간 측정 같은 **크기와 무관한 고정 시간**이 포함되기 때문입니다. 3×3은 계산이 매우 짧아서 이 고정 시간의 비중이 큽니다.
5. 실제로 연산 1회당 시간(평균 시간 ÷ N²)을 구하면 3×3은 약 0.000458 ms, 25×25는 약 0.000105 ms입니다. 크기가 클수록 고정 시간이 많은 연산에 나뉘어 1회당 시간이 줄어듭니다.
6. 고정 시간의 영향이 작은 13×13과 25×25를 비교하면, 연산 횟수는 약 3.70배(625 ÷ 169) 늘고 시간은 0.016550 ms에서 0.065330 ms로 약 3.95배 늘었습니다. 이 값이 연산 횟수 배율에 더 가까운 것으로 보아, 크기가 충분히 클 때 시간이 N²에 비례한다는 것을 확인했습니다.
7. 결론적으로 패턴 크기가 N배 커지면 연산량은 N²배 늘어나므로, 큰 이미지를 다루는 AI는 같은 계산을 동시에 처리하는 병렬 처리 장치(NPU)가 필요해집니다.
